Core questions

The same for every candidate.

MustRuns PostgreSQL in production (schema design, indexes, query plans)· 6 min

Tell me about a PostgreSQL database you were responsible for in production. What did you change in its schema or indexes, and how did you decide?

Follow-ups

  • How did you read the query plan, and what did it show?
  • What would you do differently now?

Strong answers include

  • owned decisions, not just used the database
  • reasons tied to query patterns or data size
  • reads EXPLAIN output

Warning signs

  • only ever used the database through an ORM someone else configured
  • can't explain why an index helped
MustShips schema and data migrations on live data safely· 7 min

Tell me about a schema or data change you shipped on a large production table. How did you avoid downtime and lock problems?

Follow-ups

  • How would you roll it back halfway through?
  • How did you backfill existing rows?

Strong answers include

  • expand-contract or backward-compatible steps
  • batched backfills
  • concurrent index builds
  • a rollback plan

Warning signs

  • only ran tool-generated migrations on small or staging data
  • no idea how long the change locked the table
ImportantZero-downtime deploys with schema changes and multiple replicas· 5 min

Imagine schema migrations run automatically when each application instance starts, and you run several instances. What can go wrong, and how would you change the process?

Follow-ups

  • How would old and new versions of the app run against the same schema during a rollout?

Strong answers include

  • spots concurrent migration races
  • moves migrations to a separate pre-deploy step
  • backward-compatible releases

Warning signs

  • doesn't see a problem
  • proposes stopping all instances for every change
ImportantDiagnoses and fixes query performance· 5 min

A list endpoint gets slower every week as data grows. It counts all rows and pages with OFFSET. How would you investigate and fix it?

Follow-ups

  • How would you prove the fix worked?

Strong answers include

  • measures first
  • EXPLAIN ANALYZE
  • keyset pagination or better indexes
  • questions the full count

Warning signs

  • jumps to caching or bigger hardware without measuring
ImportantProduction Python with an ORM (SQLAlchemy/SQLModel ideal)· 4 min

In an ORM you've used in production, how have you dealt with queries that loaded far more data, or ran far more queries, than expected?

Follow-ups

  • How did you find out it was happening?

Strong answers include

  • N+1 queries
  • eager vs lazy loading
  • looked at the generated SQL

Warning signs

  • treats the ORM as a black box
ImportantBuilds reliable database test setups· 4 min

How would you set up tests for database code so that tests can't affect each other, and still run quickly?

Follow-ups

  • How would you test the migrations themselves?

Strong answers include

  • per-test transactions or rollback
  • containers or a real database in CI
  • fixtures or factories

Warning signs

  • one shared database with cleanup at the end
  • mocks the database entirely for DB logic
ImportantPostgreSQL operations: backups, pooling, replication, monitoring· 4 min

What would you put in place first to make a single production PostgreSQL instance reliable, and why that order?

Follow-ups

  • How would you know a backup actually works?

Strong answers include

  • backups with tested restores
  • connection pooling
  • slow-query monitoring
  • prioritises by risk

Warning signs

  • backups never restored
  • no mention of monitoring

Personal questions

Based on this candidate’s CV.

Deep dive into a CV claimImportantDiagnoses and fixes query performance· 5 min

You cut p95 latency of account listing from 900 ms to 40 ms. Walk me through how you found the bottleneck and what you changed.

From the CV: “Cut p95 latency of account listing from 900 ms to 40 ms with EXPLAIN ANALYZE, composite indexes and keyset pagination”

Why ask: Tests whether the result came from her own diagnosis, and how she measures.

Follow-ups

  • What did the plan look like before and after?
  • What did keyset pagination break, if anything?

Strong answers include

  • specific plan nodes or index choices
  • before/after measurement

Warning signs

  • vague about her own part
Deep dive into a CV claimMustShips schema and data migrations on live data safely· 5 min

You added a column to a 200M-row table and rebuilt indexes concurrently. What was the riskiest moment, and how did you protect production?

From the CV: “added a 200M-row table column and rebuilt indexes with CREATE INDEX CONCURRENTLY”

Why ask: Checks depth on the exact skill the role needs most.

Follow-ups

  • What happens if a concurrent index build fails halfway?

Strong answers include

  • invalid index cleanup
  • lock timeouts
  • monitoring during the change

Warning signs

  • no plan for failure
Probe a gapImportantPostgreSQL operations: backups, pooling, replication, monitoring· 4 min

Have you been responsible for backups and restores of a production database? Tell me about the last restore you did or tested.

Why ask: Her CV covers pooling and monitoring but not backups or recovery.

Follow-ups

  • How long did the restore take, and was that acceptable?

Strong answers include

  • has actually restored
  • knows recovery time

Warning signs

  • assumes backups work without testing
